# Інструменти: тести ядра без Unity

## Навіщо це

Ядро `Game.Core` навмисно спроектоване без залежностей від рушія
(asmdef: `noEngineReferences: true`, жодного `using UnityEngine`). Завдяки
цьому вся ігрова логіка — Напруга, конвеєр доби, шар сигналів, економіка,
прокачка — **компілюється і тестується звичайним .NET, без запуску редактора**.

Виграш: цикл правки займає секунди, а не «відкрий Unity і подивись». І
асистент може перевіряти свій код сам, а не віддавати неперевірене.

## Як користуватися

```bash
./tools/run-tests.sh            # прогнати всі тести
./tools/setup-dotnet.sh         # встановити .NET SDK (потрібно один раз)
```

Або напряму:

```bash
dotnet test tools/Alpha.Headless.sln
```

У хмарних сесіях SDK встановлюється автоматично — див. `.claude/hooks/session-start.sh`.

## Як це влаштовано

| Файл | Що робить |
|---|---|
| `Game.Core.Headless/Game.Core.csproj` | Збирає ядро під `netstandard2.0`. Файли **не копіюються** — підключаються посиланням на `Assets/_Project/Scripts/Core/**`, тому headless і редактор не можуть розійтися |
| `Game.Tests.Headless/Game.Tests.EditMode.csproj` | Ті самі тести, що бачить Unity Test Runner. Ім'я збірки задано явно — від нього залежить `InternalsVisibleTo` в ядрі |
| `Game.Tests.Headless/UnityShim.cs` | Заглушка `UnityEngine.Application.dataPath` для архітектурних тестів, які грепають вихідники. Лежить **поза** `Assets/`, тому Unity її не бачить |
| `Game.Gameplay.Lint/` | Компілює Unity-обгортки **і редакторні скрипти** із заглушками UnityEngine/UnityEditor. Ловить звичайні помилки C# (описки, забуті using, звернення до `internal`-членів ядра) без запуску редактора |
| `Alpha.Headless.sln` | Щоб `dotnet test` працював однією командою |

## Межі

Покривається **лише `Game.Core`** — це вся ігрова логіка (37 файлів із 42).

**`Game.Gameplay` і `Game.Gameplay.Editor` покриті лише лінтом збірки**:
заглушки перевіряють, що код компілюється, але НЕ перевіряють поведінку рушія —
серіалізацію, інспектор, життєвий цикл MonoBehaviour. Сцени, префаби, імпорт
асетів і збірка білда — теж лише в редакторі.

Для редакторного коду ця межа особливо вузька: він майже цілком складається з
викликів Unity API, а сигнатури цих викликів оголошені в **нашій же** заглушці.
Лінт підтверджує узгодженість коду із заглушкою, а не зі справжнім
редактором. Тому поверхня викликів там навмисно тримається вузькою.

Тому зелені headless-тести означають «логіка вірна», але не скасовують
перевірку в Unity перед релізом.

## Важливі тонкощі

- **NUnit 3.14, не 4.x.** У четвертій версії класичний API
  (`Assert.AreEqual`, `IsTrue`, `Greater`, `IsEmpty`) переїхав у `ClassicAssert`.
  У нас таких викликів більше сімдесяти — на 4.x усе розвалиться, і headless-версія
  тестів розійдеться з тією, що ганяє Unity.
- **Ім'я тестової збірки** зобов'язане бути рівно `Game.Tests.EditMode`: в ядрі стоїть
  `[assembly: InternalsVisibleTo("Game.Tests.EditMode")]`, а тести чіпають
  `internal`-члени. Інше ім'я — і отримаєте `CS0122` у п'яти місцях.
- **`.gitignore`** ігнорує `*.csproj` і `*.sln`, тому що Unity генерує
  свої. Для `tools/` стоять винятки — інакше ці файли мовчки не закомітяться.

## Симуляційний харнес

```bash
dotnet run --project tools/Alpha.Sim -- --days 200 --out sim-out
```

Ганяє дванадцять кампаній (три політики гравця × чотири тири) і пише
`sim-out/trace-*.csv` — по рядку на фазу, з усіма числами, включно з прихованими:
значення Напруги, смуга, заряд кожного накопичувача, яка ступінь
передвісника реально дійшла до гравця, які сигнали показані, що спрацювало.
Плюс `sim-out/summary.csv` — зведення по кампаніях.

Навіщо: детермінізм ядра оплачений дорого, а головну його вигоду ми не
використовували. Раз кампанія відтворювана до байта, темп можна ВИМІРЯТИ.
Питання «на яку добу гравець побачить першу подію» перестає бути предметом
суперечки і стає числом.

Метрики рахує `Game.Core.Sim.CampaignSimulator.Measure`, і **ті самі метрики
читають тести темпу** (`CampaignPacingTests`), тому CLI і CI дивляться на ті самі
числа. Тест стверджує вікно, а не точку: «перший інцидент між 4-ю і
20-ю добою» — це дизайн-рішення, а конкретне число всередині вікна —
плейсхолдер, який буде рухатися.

Харнес читає `internal`-члени ядра (заряди, значення Напруги) — це
інструмент дизайнера. `Game.Gameplay` такого доступу не отримує і отримати не
може, тому дашборд у самій грі, як і раніше, неможливо зібрати навіть по
помилці (інваріант 3).

## Віддати зріз тестеру

```powershell
powershell -File tools/publish-play.ps1
```

Прогонює тести, потім публікує `Build/Play` — самодостатній каталог
(~65 МБ): `Alpha.Play.exe`, `play.cmd` для подвійного кліку і `ЧИТАЙ.txt` з
інструкцією і питаннями до тестера. **.NET тестеру встановлювати не потрібно**: рантайм
усередині.

Подвійний клік запускає гру з рішеннями; вікно не закривається по закінченні,
інакше підсумок на п'яту добу майнув би і зник.

## Візуальна сцена і Unity-білд

```powershell
powershell -File tools/build-unity.ps1
```

Збирає сцену «Відкриття» (меню **Alpha → Перестворити сцену «Відкриття»**) і
Windows-білд у `Build/Windows`. Портретна сцена перших діб — та сама, що
друкує текстова збірка: обидві читають ОДНІ дані (`OpeningScenes`), рахує
кадр ядро (`ScenePlayback`), а малює рушій.

Портрети кладуться за ключем у `Assets/Resources/Portraits/<id>.png`. Файлу немає
— сцена все одно грається, замість портрета іменна заглушка: художник
додає картинку, не чіпаючи код. Подробиці — `docs/ASSETS.md`.

Сцена в репозиторій не кладеться навмисно: вона посилається на скрипти за GUID
з `.meta`, тому генерується на місці.

### Автотур, що не заважає на екрані

```powershell
powershell -File tools/run-offscreen.ps1 -GameArgs "-autoplay -autoplay-journal"
```

Запускає `Build/Windows/Alpha.exe` у вікні 1600×900 і одразу, щойно вікно
з'являється, відсуває його за правий край усіх моніторів; гра далі малює й
знімає (згорнута — не малювала б). Код виходу — код гри; `-TimeoutSec`
(900 за замовчуванням) зупиняє зависле, `-ParkDelayMs` відкладає ховання.
Аргументи гри — ОДНИМ рядком: у режимі `-File` PowerShell не робить із «a,b»
масив.

## Консольна збірка першої години

```bash
dotnet run --project tools/Alpha.Play -- --auto          # прогін політикою
dotnet run --project tools/Alpha.Play                    # грати руками
dotnet run --project tools/Alpha.Play -- --auto --days 40 --path bloody
dotnet run --project tools/Alpha.Play -- --auto --save slice.save
dotnet run --project tools/Alpha.Play -- --auto --load slice.save --days 3
```

Зріз із `docs/FIRST_HOUR.md` §4 п. 6, який програється текстом: цикл «ранок —
розстановка — день — рішення — ніч — вибір ночі», репліки міста за ключами,
підсумок на п'яту добу, збереження і завантаження.

Світ будується спільним із харнесом кодом (`tools/Shared/SettlementWorld.cs`) —
інакше виміряний темп стосувався б не тієї гри, в яку грали.

Внутрішніх членів ядра збірка НЕ бачить, на відміну від харнеса: це гра, а грі
приховані числа недоступні (інваріант 3). Тому назовні йдуть смуги
(`Напруга: Calm`), а не значення, і пости роздаються публічним
`BaseState.TryAssign` — тим самим шляхом, що й у самій грі.

`--auto` не для зручності: він робить зріз відтворюваним. Прогін руками і
прогін політикою йдуть по одному коду, тому «у мене було не так»
перевіряється однією командою.

**Що збірка вже виміряла (20.09.2026).** За п'ять діб стартового хутора не
трапляється жодної пригоди і жодного рішення гравця — зріз друкує про
це попередження. Перше рішення приходить приблизно на дванадцяту добу, за
сорок діб їх чотири. Це не поломка конвеєра (на сорока добах усе
працює), а відсутність авторського контенту відкриття: два стартові інциденти,
вузол із розв'язками і передвісник «Тугар» — крок 5 порядку збірки. Поки його немає,
перша година порожня, і це видно числом, а не на слух.
