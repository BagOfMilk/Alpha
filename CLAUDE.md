# CLAUDE.md — память проекта для AI-ассистента (Alpha)

> Этот файл читают и облачный, и локальный Клод. Он держит контекст в репозитории,
> а не в памяти одного чата — чтобы любой ассистент был сразу в курсе.

## Что это
Base-builder RPG на **Unity 6.4 (6000.4.10f1)**. **Главный луп — городской:**
жизнь поселения день за днём, назначения, события, фракции, рост от хутора до
городка. Вылазки — источник материалов, преимущественно тихие. **Бои очень
редкие** (Поправка №3).

## Источник истины
**`docs/GDD.md`** — дизайн-документ (GDD v6) + **`docs/GDD_AMENDMENTS.md`** —
поправки владельца проекта. Все решения по механикам там.
Формулы городского слоя — **`docs/SETTLEMENT_LAYER.md`**.
**При конфликте: поправки > GDD > дизайн-доки > код.**

> `docs/DESIGN.md` и `docs/BALANCE.md` — **исторические**, источником истины
> не являются (там отменённые решения: XCOM-фазы, шесть ресурсов и т.п.).

## Ключевые решения (зафиксированы)
- **Движок:** Unity 6.4 (6000.4.10f1).
- **Столп «Ненасилие прежде всего» (Поправка №1):** у любой задачи есть
  ненасильственный путь (безопасный, но медленный и дорогой);
  насильственный путь есть всегда — **очень сложный, но быстрый**.
  Ось баланса «время против риска».
- **Кастинг персонажей (Поправка №2):** все именные персонажи (напарники,
  NPC, лидеры фракций, боссы) — переосмысленные персонажи из
  **общественного достояния** (мифология/фольклор/классика до ~1930;
  только первоисточники, без охраняемых поздних версий и trademark-имён).
  У каждого — поле «Первоисточник». Протагонист — кастомный.
- **Живой слой поселения (Поправка №3):** городской цикл — главный луп; бои
  редкие; дуга кампании хутор → село → слобода → городок; **полный детерминизм**
  (см. инварианты); слой сигналов — часть системы, а не UI; список драйверов
  Напряжения закрыт; правило новой шкалы «якорь + потребитель + сигнал».
  Первый чек-пойнт разработки — **срез городского цикла (30 дней)**, а не боя.
- **Боёвка:** модель **Wasteland 3** — пул AP (~8–10), индивидуальная инициатива
  вперемешку, укрытия + надёжный %, плоская броня (1–2) + пробитие/шред, overwatch,
  слой состояний. **НЕ** XCOM-фазы. Тюнинг — под «очень сложно» (Поправка №1).
- **Модель персонажа (Эпик 2):** 4 атрибута (Сила/Ловкость/Смекалка/Воля),
  10 скилов (без классов), трейты-слоты, шрамы на отдельном вечном треке.
  Правило **«один эффект — одна система»**.
- **Архитектура (Эпик 18):** контент через ScriptableObject; **единый агрегатор
  модификаторов статов** (US-18.2); числа баланса — в `BalanceConfig`-SO,
  правятся без перекомпиляции.

## Инварианты, которые нельзя нарушать
1. **В ядре нет `System.Random`.** Планировщик событий — детерминированный
   накопитель. Непредсказуемость берётся из неполноты информации.
2. **Не менее трёх активных накопителей** с разными ставками, и ставки меняются
   от действий игрока — иначе детерминизм читается насквозь.
3. **Числовые поля дневного отчёта — `internal`.** `Game.Gameplay` физически не
   может прочитать Напряжение: дашборд невозможно собрать даже по ошибке.
4. **Нет немого перехода полосы** — смена полосы любой скрытой шкалы обязана
   породить наблюдаемый сигнал.
5. **Список драйверов Напряжения закрыт.** Новые системы модулируют
   существующие драйверы, но не добавляют своих.
6. **Новая шкала требует трёх вещей:** якорь (что означает значение),
   потребитель (формула, которая её читает), сигнал (как игрок её увидит).
7. **Порядок шагов дня — только через `DayStepOrder`** (константы в одном файле).
8. **Проверки детерминированные:** «скил ≥ порога», порог показан заранее.
   Полосы исхода (Поправка №3.7) — расширение, а не замена.
9. **Названия конкретных настольных систем-источников не упоминаются** нигде:
   ни в коде, ни в документации, ни в коммитах, ни в титрах. Пишем
   «настольные системы управления владением».

## Структура кода
- `Assets/_Project/Scripts/Core` — чистый C# (asmdef `Game.Core`,
  `noEngineReferences`): логика и данные, без UnityEngine → тестируемо.
- `Assets/_Project/Scripts/Gameplay` — тонкие обёртки Unity (SO, MonoBehaviour).
- `Assets/Tests/EditMode` — юнит-тесты (`Game.Tests.EditMode`).
  **Прогонять после изменений.**
- `tools/` — headless-проекты: ядро компилируется и тестируется **без Unity**.

## Проверка кода (обязательно перед push)
```bash
./tools/run-tests.sh        # или: dotnet test tools/Alpha.Headless.sln
```
Ядро не зависит от движка, поэтому вся логика проверяется за секунды обычным
.NET. В облачных сессиях SDK ставится автоматически (`.claude/hooks/session-start.sh`),
на каждом пуше тесты гоняет CI (`.github/workflows/core-tests.yml`).

**Границы:** покрывается только `Game.Core`. `Game.Gameplay` (MonoBehaviour,
ScriptableObject), сцены и билд — только в Unity. Подробности — `tools/README.md`.

**Городской слой (проектируется):** namespace `Game.Core.{Pressure, World,
Settlement, Factions, Checks, Signals, Loop}`. Они **не ссылаются** на
`Game.Core.Stats` и `Game.Core.Economy` — только через порты `SkillKey` /
`ISettlementActor` / `CostBundle`, потому что эти типы будут переписаны.
